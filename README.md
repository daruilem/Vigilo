# Vigilo

**A free, readable security check-up for small websites.**

Vigilo checks a website's certificate, security headers, exposed files, email security,
platform and privacy basics, then explains in plain language what is wrong and exactly
how to fix it, for the hosting the site runs on. It is built for the people who run
most of the web without a security team: small businesses, associations, freelancers
and the agencies who build their sites.

> Vigilo is Latin for *"I keep watch"*.

## Why

Tools like SSL Labs or Mozilla Observatory are excellent, but they speak to engineers.
A shop owner who reads *"X-Frame-Options missing"* does not know whether it matters or
what to do. Vigilo keeps the technical rigour and adds:

- **a sentence anyone understands** for every result, and why it matters,
- **the raw value that was observed**, so a technician can verify it,
- **copy-ready fixes for Apache, Nginx, Cloudflare and WordPress**,
- **a letter grade (A to F)** and a printable report to hand to a web agency.

## What it checks

| Area | Checks |
|---|---|
| TLS | Certificate trusted and covering the domain, days before expiry, TLS 1.0/1.1 refused, TLS 1.2/1.3 offered (rules from **BSI TR-03116-4**), HTTP to HTTPS redirect |
| HTTP headers | HSTS, Content-Security-Policy, clickjacking protection, `nosniff`, Referrer-Policy, Permissions-Policy, software version disclosure |
| Sensitive files | `/.git/HEAD`, `/.git/config`, `/.env`, common backups and database dumps. **Status code and size only: content is never read.** |
| Email security | SPF (presence, `+all`, `?all`, duplicates, 10-lookup limit counted across nested includes), DMARC policy, DKIM under 15 common selectors. The mail provider is recognised from MX records to suggest a ready-made SPF record. |
| Platform | WordPress, Joomla, Drupal, PrestaShop, Shopify, Wix, Squarespace, Webflow; visible version; WordPress core and plugins compared with their latest release on wordpress.org |
| Privacy and legal *(not graded)* | Google Fonts loaded from Google (LG München I, 3 O 17493/20), trackers without a consent tool, privacy policy link, Impressum for German and Austrian sites (§ 5 DDG), mentions légales for French sites (art. 6 LCEN) |

Privacy and legal points appear in the report but do not change the security grade.

## Interface

The web interface (`web/`) looks like a printed inspection report rather than a
dashboard: paper and ink colours, one stamp blue for the verdict, red, amber and green
strictly for results, and every technical value set in monospace.

- **Check-up**: address field and a mandatory authorisation checkbox.
- **Live log**: each step appears as the server reports it (Server-Sent Events).
- **Report**: grade stamp, one section per problem (observed value, why it matters,
  fix per hosting with a copy button), passed checks folded at the end.
- **PDF download**: a real PDF generated by the server in the reader's language (right-to-left for
  Arabic), with the fixes for the chosen hosting. Reports are signed, so an edited report
  cannot be turned into an official-looking PDF.
- **Method**: the exact list of checks, the limits of the tool and what is kept.
- **Four languages**: English (default), French, German and Arabic, with a full
  right-to-left layout for Arabic. Addresses carry the language (`/en`, `/fr`, `/de`,
  `/ar`) so a shared link opens in the right language.

Accessibility target is WCAG 2.1 AA: contrast checked for every colour, full keyboard
use (tabs follow the WAI-ARIA pattern), visible focus, layout from 360 px. Fonts are
self-hosted at build time, so visitors' browsers never contact Google.

## Quick start

### Docker

```bash
docker compose up --build
# web: http://localhost:3000   API: http://localhost:8000
```

### Published images

Each release publishes signed images to GitHub Container Registry:

```bash
docker pull ghcr.io/daruilem/vigilo-api:0.1.0
docker pull ghcr.io/daruilem/vigilo-web:0.1.0
```

The web image is built for an API at `http://localhost:8000`; to serve it from another
address, build it yourself with `--build-arg NEXT_PUBLIC_VIGILO_API_URL=...`.

#### Verifying the images

Images are signed without long-lived keys: the signature proves the image was built by
this repository's release workflow from a tag.

```bash
cosign verify ghcr.io/daruilem/vigilo-api:0.1.0 \n  --certificate-identity-regexp '^https://github.com/daruilem/Vigilo/\.github/workflows/release\.yml@refs/tags/v' \n  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

The SBOM (SPDX) of each image is attached to the GitHub release and to the image itself
(`docker buildx imagetools inspect ghcr.io/daruilem/vigilo-api:0.1.0 --format '{{ json .SBOM }}'`).

### Local development

Requires Python 3.10+ and Node.js 22+.

```bash
git clone https://github.com/daruilem/Vigilo.git
cd vigilo

# API
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
uvicorn vigilo.api:app --reload  # http://localhost:8000

# Web interface, in a second terminal
cd web
npm install
npm run dev                      # http://localhost:3000
```

### Command line

```bash
vigilo scan example.com               # human-readable report
vigilo scan example.com --json        # machine-readable JSON
vigilo scan example.com --fail-under 80   # exit code 2 if the score is below 80 (CI use)
vigilo scan example.com --lang de --markdown report.md --platform nginx
                                      # German report, also appended as Markdown
```

### GitHub Action

Check your website on every deployment, with the grade and the fixes in the job summary:

```yaml
- uses: daruilem/Vigilo@v0.1.0
  with:
    target: www.example.com    # a site you run
    fail-under: 80             # optional: fail the job below this score
    lang: en                   # en, fr, de or ar
    platform: nginx            # apache, nginx, cloudflare or wordpress
```

Outputs: `score`, `grade` and `report` (path of the JSON report). To check a staging
container started earlier in the same job, add `allow-private: "true"`. Inputs reach
the shell only through environment variables, and values read from the website are
escaped before they enter the Markdown summary.

### HTTP API

| Endpoint | Description |
|---|---|
| `POST /api/v1/scans` | Body `{"target": "example.com", "authorized": true, "lang": "en"}`. Returns the report. |
| `GET /api/v1/scans/stream?target=…&authorized=true&lang=en` | Server-Sent Events: `progress`, then `report` or `failure`. |
| `POST /api/v1/reports/pdf` | Body `{"report": <signed report>, "lang": "en", "platform": "nginx"}`. Returns the PDF. |
| `GET /health` | Liveness check. |

Errors carry a stable code (`invalid_target`, `dns_error`, `forbidden_target`,
`unreachable`, `timeout`, `too_many_redirects`, `not_authorized`, `rate_limited`,
`target_rate_limited`, `busy`) and a one-sentence message that says what happened and
what to do.

### Configuration

| Variable | Default | Purpose |
|---|---|---|
| `VIGILO_CORS_ORIGINS` | `http://localhost:3000` | Origins allowed to call the API |
| `VIGILO_TRUSTED_PROXIES` | *(none)* | IPs or CIDR ranges of your reverse proxies. Only then is `X-Forwarded-For` believed. |
| `VIGILO_SCANS_PER_WINDOW` | `10` | Scans per client IP per window |
| `VIGILO_SCANS_PER_TARGET` | `3` | Scans of the same website per window, all clients together |
| `VIGILO_WINDOW_SECONDS` | `600` | Length of the rate-limit window |
| `VIGILO_MAX_CONCURRENT_SCANS` | `8` | Scans running at the same time before answering `busy` |
| `VIGILO_SCAN_TIME_LIMIT` | `60` | Seconds before a scan is stopped |
| `VIGILO_DOCS` | `0` | Set to `1` to serve the interactive API docs at `/docs` |
| `VIGILO_SIGNING_KEY` | random at start-up | Secret used to sign reports. Set it when running several API processes. |
| `VIGILO_PDFS_PER_WINDOW` | `30` | PDF downloads per client IP per window |
| `VIGILO_VERIFICATIONS_PER_WINDOW` | `20` | Domain ownership requests per client IP per window |
| `NEXT_PUBLIC_VIGILO_API_URL` | `http://localhost:8000` | API address used by the web interface (build time) |
| `NEXT_PUBLIC_VIGILO_ACTIVE_SCAN` | `0` | Set to `1` to show the domain ownership verification (preview of the active scan, in progress) |

## Security of Vigilo itself

A security tool has to be beyond reproach. Vigilo's own site passes all of Vigilo's
header checks, and the service is hardened against being turned into a weapon:

- **SSRF and DNS rebinding.** Every connection, including each redirect, resolves the
  host once, refuses private, loopback and link-local addresses, then connects to that
  exact address. Raw TLS probes reuse the addresses validated at the start of the scan.
- **Signed reports.** Reports are not stored, so the browser sends them back to get a PDF;
  an HMAC signature makes edited or invented reports useless.
- **Resource limits.** Request bodies are capped at 1 MB, page bodies at 2 MB, every request has a 10 s
  timeout, a whole scan is stopped after 60 s, and concurrent scans are capped.
- **Abuse limits.** Per-IP and per-target rate limits; `X-Forwarded-For` is only
  trusted from configured proxies, so it cannot be forged to reset a quota.
- **Web interface.** Strict Content-Security-Policy with a fresh nonce per request (no
  `'unsafe-inline'`), `frame-ancestors 'none'`, HSTS, `nosniff`, Referrer-Policy,
  Permissions-Policy and Cross-Origin policies on every response. No source maps in
  production, no `X-Powered-By`, and a lint rule that forbids any `console` output.
- **API.** Security headers and `Cache-Control: no-store` on every response, no
  `Server` header, interactive docs off by default, generic error messages that never
  expose internals.
- **Containers.** Non-root users, read-only file systems, all Linux capabilities dropped.
- **Supply chain.** Dependabot keeps Python, npm, Actions and base images up to date,
  CodeQL analyses every change, and released images are signed with Sigstore and ship
  with an SBOM and build provenance (see [Verifying the images](#verifying-the-images)).

Code that runs in a browser is always visible to its user; Vigilo's front end simply
contains nothing secret.

## Architecture

```
src/vigilo/                 Python package (API, CLI, scanner)
├── checks/                 one module per check, same interface
│   ├── base.py             Check + ScanContext
│   ├── tls.py  headers.py  files.py
│   ├── email.py            SPF, DMARC, DKIM (dnspython)
│   ├── cms.py              platform detection, WordPress updates
│   └── privacy.py          fonts, trackers, legal pages
├── models.py               Finding and ScanReport: the only contract between parts
├── guidance.py             reader-facing text: headlines, fixes per hosting, follow-ups
├── i18n.py  locales/       report translation (fr, de, ar)
├── pdf/                    PDF rendering (ReportLab, right-to-left for Arabic), fonts (OFL)
├── signing.py              HMAC signatures of reports
├── scanner.py              connect step, concurrent checks, progress events
├── scoring.py              score (0-100) and grade (A-F)
├── net.py                  hardened HTTP client (public addresses only, capped bodies)
├── target.py               input validation
├── htmlscan.py             safe HTML reading (standard library parser)
├── clientip.py  ratelimit.py
├── api.py                  FastAPI: JSON and Server-Sent Events
└── cli.py
web/                        Next.js (App Router), TypeScript, Tailwind CSS
└── src/
    ├── proxy.ts            per-request CSP nonce
    ├── app/[lang]/         pages, one URL prefix per language
    ├── i18n/               interface text in en, fr, de, ar
    ├── components/         Checkup flow, Report, FixTabs, ScanLog, GradeStamp…
    └── lib/                API client, types mirroring the Python models
```

Design principles:

- **Translation without touching the checks.** Checks write English; catalogs in
  `src/vigilo/locales/` map each exact sentence (or template such as
  `"The certificate expires in {days} days."`) to French, German and Arabic. A test drives
  every check through all its branches and fails if any sentence is left untranslated.
- **Detection and wording are separate.** Checks decide pass or fail and record what
  they observed; `guidance.py` holds most sentences and code snippets shown to readers.
- **Network I/O is thin, decision logic is pure** and unit-tested without the network.
  Scanner and API tests run against in-memory transports.
- **One request per resource.** The home page is fetched once and shared by all checks.
- **A failing check never breaks a scan.** It is reported as "could not be checked".

### Adding a check

1. Create `src/vigilo/checks/my_check.py` with a `Check` subclass (`name`, `label`).
2. Put the decision logic in pure functions and test them in `tests/`.
3. Add headlines and fixes for its finding ids in `guidance.py`.
4. Register an instance in `ALL_CHECKS` in `src/vigilo/checks/__init__.py`.

## Legal and ethics

Checking a system without permission can be a criminal offence, for example under
§§ 202a and 202c of the German Criminal Code (StGB), Article 323-1 of the French Penal
Code or Articles 394 bis ff. of the Algerian Penal Code. Vigilo is designed to stay on
the safe side:

- **Explicit authorisation.** Every scan requires the user to confirm they run the
  site or have permission to check it. The API refuses scans without it.
- **Passive only.** Vigilo does what a browser or a mail server does: it loads the home
  page, reads headers, performs TLS handshakes, reads public DNS records and requests a
  short list of well-known paths. It never sends forms, guesses passwords or tries
  exploits.
- **Sensitive files are never read.** For paths like `/.env`, only the status code,
  declared size and content type are used. The body is not downloaded, shown or stored.
- **Polite and identifiable.** At most 3 requests at once, a `Vigilo/<version>`
  User-Agent, and limits per client and per target site.
- **Nothing stored.** Reports only exist in the response. The rate limiter keeps
  counters in memory for 10 minutes.

Only scan websites you run or have permission to test. Legal findings are reminders,
not legal advice.

## Known limitations

- Not a penetration test: a good grade does not mean a site cannot be attacked.
- Only the home page is analysed.
- Sites that answer every path with an HTML page hide sensitive files from the check
  (HTML answers are ignored to avoid false alarms).
- TLS 1.0/1.1 can only be tested if the scanning machine's OpenSSL still supports them.
- DKIM keys under unusual selectors cannot be found: DNS offers no way to list them.
- Plugin versions come from the `?ver=` parameter of their files; plugins that hide it, and
  premium plugins absent from wordpress.org, are not compared.
- Content added by JavaScript is not analysed: that would mean running a full browser on
  the server, which is heavy and widens the attack surface.
- Rate limits live in one process; several API workers need a shared store.
